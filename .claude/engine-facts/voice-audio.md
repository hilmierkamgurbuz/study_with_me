# voice-audio — Unity audio/mic/WebSocket facts backing the Voice system

- `Microphone.Start(deviceName, loop, lengthSec, frequency)` records into a circular `AudioClip` of that fixed length; `Microphone.GetPosition(deviceName)` returns the current write-head sample index, wrapping at `lengthSec * frequency`. Reading new audio means tracking the last-read position and pulling only the delta via `AudioClip.GetData`, handling the wrap as two reads (tail then head) rather than assuming a fixed chunk size or a single contiguous read.
- `AudioClip.Create(name, lengthSamples, channels, frequency, stream: true, pcmReaderCallback)` creates a streaming clip whose `pcmReaderCallback` is invoked by Unity's **audio thread**, not the main thread, whenever the DSP graph needs more samples. The callback must never allocate and must never block — it may only read from a plain, pre-allocated buffer.
- Consequence: a single producer (main-thread network/decode) writing into a fixed-size ring buffer, and a single consumer (the audio-thread callback) reading from it, is the only safe shape. A plain `lock` around index updates is acceptable here — both sides do a tiny, bounded amount of work per call, so lock contention is not a realistic concern at this frequency.
- NativeWebSocket (`endel/NativeWebSocket`) queues incoming frames internally and only invokes `OnOpen`/`OnMessage`/`OnError`/`OnClose` from `DispatchMessageQueue()`, which must be polled every frame (from `Update()`) on non-WebGL platforms. As long as that's polled, WS→Unity-API calls already happen on the main thread — no separate marshaling queue is needed for the WebSocket side; only the audio ring buffer needs its own producer/consumer safety (above).
- `Microphone.End(deviceName)` stops recording. The `AudioClip` Microphone allocates for recording is a distinct object from any playback `AudioClip` — never the same buffer that's streamed back out.
- Gemini Live audio rates are asymmetric: input (mic → server) is 16kHz mono PCM16; output (server → speakers) is 24kHz mono PCM16. Treating them as the same rate is a real, easy-to-make bug.
