# voice-audio — Unity audio/mic/WebSocket facts backing the Voice system

- `Microphone.Start(deviceName, loop, lengthSec, frequency)` records into a circular `AudioClip` of that fixed length; `Microphone.GetPosition(deviceName)` returns the current write-head sample index, wrapping at `lengthSec * frequency`. Reading new audio means tracking the last-read position and pulling only the delta via `AudioClip.GetData`, handling the wrap as two reads (tail then head) rather than assuming a fixed chunk size or a single contiguous read.
- `AudioClip.Create(name, lengthSamples, channels, frequency, stream: true, pcmReaderCallback)` creates a streaming clip whose `pcmReaderCallback` is invoked by Unity's **audio thread**, not the main thread, whenever the DSP graph needs more samples. The callback must never allocate and must never block — it may only read from a plain, pre-allocated buffer.
- Consequence: a single producer (main-thread network/decode) writing into a fixed-size ring buffer, and a single consumer (the audio-thread callback) reading from it, is the only safe shape. A plain `lock` around index updates is acceptable here — both sides do a tiny, bounded amount of work per call, so lock contention is not a realistic concern at this frequency.
- NativeWebSocket (`endel/NativeWebSocket`) queues incoming frames internally, but the installed revision (`com.endel.nativewebsocket@c612a4fef60f`, `WebSocket.cs:106`) **captures `SynchronizationContext.Current` in its constructor and posts messages and events to it itself**. Constructed on Unity's main thread, that means `OnOpen`/`OnMessage`/`OnError`/`OnClose` arrive on the main thread *whether or not anyone calls `DispatchMessageQueue()`* — the `Update()` poll is a fallback for the no-context case, not the delivery mechanism. Two consequences, and the second is the one that bites: WS→Unity-API calls need no extra marshaling queue; and **a socket that is dropped without being closed is still live and still delivering** — replacing `_ws` does not silence the old one. A socket being replaced must be closed (`Close()` if Open, `CancelConnection()` if still connecting — `Close()` returns silently on a socket that is not Open), and callbacks must be scoped to the socket that registered them, or an abandoned connection writes a second voice into the playback buffer and its late `OnClose` is read as the current connection dropping.
- Gemini Live delivers a turn's output audio **faster than it is spoken** — generation runs ahead of playback, so seconds of a single turn can be in the buffer at once. A playback ring sized for network jitter rather than for a whole turn will lap itself, and the overflow policy is what the user hears: advancing the read cursor to make room leaves the cursors adjacent, so every DSP block (1024 samples ≈ 21ms at 48kHz) reads from somewhere else in the utterance and one sentence is heard shredded into another. Dropping the newest samples instead degrades to a clean truncation.
- Interrupting the model is not complete when the local buffer is flushed: the server goes on sending the abandoned turn's audio until it processes the interruption, and that tail lands *after* the flush, in front of the reply to what was just said. `serverContent.interrupted` is the acknowledgement that it has stopped; incoming audio between the local flush and that ack belongs to the turn nobody wants any more.
- `Microphone.End(deviceName)` stops recording. The `AudioClip` Microphone allocates for recording is a distinct object from any playback `AudioClip` — never the same buffer that's streamed back out.
- Gemini Live audio rates are asymmetric: input (mic → server) is 16kHz mono PCM16; output (server → speakers) is 24kHz mono PCM16. Treating them as the same rate is a real, easy-to-make bug.
