# fingerprint — project profile

- **Space model:** 3D, free/continuous transforms (no grid). One static room scene; the only "camera movement" is a lerp between two hand-placed poses (default view, TV-focus view). No procedural layout, no tile/unit size to fix.
- **Determinism:** Not required. This is a real-time voice conversation app (Gemini Live audio round-trips, human speech timing), not a simulation/replay/lockstep system. No float-tolerance concern beyond normal audio-sample precision.
- **Data authorities:**
  - `StudentProfile` fields → written only by `ProfileMerger` (loaded/saved via `IProfileRepository`). No other code assigns profile fields directly.
  - Session flow state → written only by `SessionFlowStateMachine.ChangeState` (called from within a state's own logic or via the `ISessionActions` facade — never by UI/Presentation reaching in directly).
  - Voice turn/connection state (`TurnState`, `ConnectionState`) → owned by `GeminiLiveVoiceSession`, exposed read-only via `IVoiceSession` events.
  - Break checkpoints / elapsed-session-minutes → owned by `SessionContext`, computed once by `BreakPlanner` (pure function, no side effects) and mutated only by `SessionActiveState`'s tick.
  - Inside the vendored minigame (D-030), three authorities the app must not fight: its **game state** → `GameManager` only (and it is what writes `Time.timeScale`, which additive loading makes a value the room shares); its **own camera's** `orthographicSize` and local Y → `CameraFit` only, every frame, `ExecuteAlways` — nothing outside may move that camera; its **save file** → `SaveService` only. Cross-boundary rule: the app loads the game's scene and hands it the screen, and otherwise writes nothing inside it.
- **Scale magnitudes (n):** Everything in this slice is small-n / effectively O(1) per frame — this is a single-user, single-character, single-room app, not a simulation with many actors:
  - Flow states: 6 (fixed, enumerable).
  - Concurrent voice sessions per client: 1.
  - Outbound audio chunks: ~5–10/sec (100–200ms chunks) while mic is open; mic is open only during PTT-hold or a scripted auto-open window, never continuously.
  - UI elements on screen at once: ~10 (caption text, PTT button, text input, HUD, break-offer prompt, ad-stub panel).
  - Break checkpoints per session: typically 1–3.
  - **The one exception, and it is not the app's own code:** the vendored `FruitMerge` minigame (D-030) does loop per frame over its board — up to ~60 fruit bodies, driven from ONE `Update` by `FruitTicker`, plus their ~60 faces from one `Update` by `FaceDirector`. That single-loop shape is the game's own answer to exactly this cost question (60 fruits × their own `Update`/`FixedUpdate` = 60 managed↔native crossings per frame, collapsed to 1), so the threshold was already applied upstream. It only runs while game mode is active, and the room's own systems are the small-n list above either way. Anything written here that touches the game's board is inside that budget, not outside it.
  - Away from the minigame there is still no per-frame loop over a large collection; the cost-model threshold in SKILL.md is not expected to bind on anything in the app itself except audio buffer handling (see performance budget).
- **Persistence:** One local JSON file, `profile.json`, in `Application.persistentDataPath`, written via Newtonsoft.Json. Carries `schemaVersion` (starts at 1); unversioned writes are never produced. Since D-030 a **second, independent** file sits beside it in the same folder: the minigame's `save.json` (high score, coins, settings, stats), owned solely by its `SaveService` and versioned by its own schema counter with a `Migrate` step. Different filename, so no collision — but they are two stores that know nothing about each other, which is deliberate: the game's progress is not part of the student profile. No cloud/account sync in this slice (explicitly deferred per the product concept itself).
- **Network model:** Two independent client-authoritative connections to Google's Gemini backend, no in-app networking/multiplayer:
  1. A WebSocket (Gemini Live API, `BidiGenerateContent`) for the voice session — turn boundaries are client-driven via explicit `activityStart`/`activityEnd` messages (manual activity signaling, automatic server-side VAD disabled — see the plan's Architecture section for why), not server-authoritative.
  2. Plain REST `generateContent` calls (via `UnityWebRequest`) for one-shot structured text tasks (end-of-session summarization).
  There is no peer-to-peer or client-authority-arbitration concern; the only "authority" question is Google's service being unavailable/erroring, handled as a fault event (`IVoiceSession.Faulted`), not a network-ownership model.
- **Performance budget:** Not a frame-rate-critical app — no large simulation, no per-frame allocation over collections. Target 60fps in Editor/Standalone as a baseline sanity check, not a hard ceiling being designed against. The one real perf-sensitive path is audio: the streaming-playback ring buffer must never allocate on the Unity audio DSP thread (fixed-size buffer, pre-allocated). Memory ceiling and load-time ceiling: **OPEN** — not yet meaningful until a mobile build target is in scope; revisit at the platform pass named in the plan's "explicitly out of scope" list.
- **Target platform/version:** Unity 6000.0.80f1, URP 17.0.4, New Input System (old Input Manager disabled) — and that stayed true through the minigame import: rather than re-enabling the legacy backend for the vendored game, its one input reader was ported (D-031), verified 2026-08-13 by a clean compile and a playable session in `Game.unity`. Nothing in this project reads the legacy `Input` API. Editor + Standalone (desktop) only for this slice. Android/iOS/WebGL are named release-scope targets but explicitly out of scope here — WebGL in particular needs a different mic/socket implementation (Unity's `Microphone` and raw sockets don't function in a browser sandbox), which is why the voice transport sits behind `IVoiceSession` rather than being called directly.
